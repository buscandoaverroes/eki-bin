## The assembly

```
                   XIAO ESP32-C3 (USB-C in)
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
     LED strip          shared GND           IMU
   5V ──── 5V         (one pad, see          3V3 ──── 3V3
   D0 ──── DIN         splice note)          D4 ───── SDA
   GND ─┐                    │               D5 ───── SCL
        └────────────────────┴──── GND ──────┘
```

### LED strip — 3 wires

| XIAO C3 | Physical position (USB-C up) | GPIO | → | Strip pigtail |
|---|---|---|---|---|
| 5V | right side, 1st from top | — | → | 5V |
| **D1** | left side, 2nd from top | **`3`** | → | DIN |
| GND | right side, 2nd from top | — | → | GND |

⚠ **This unit uses D1/GPIO3, not the D0/GPIO2 that
[xiao_esp32c3.md](xiao_esp32c3.md) documents as the board's default LED
pin.** A soldering mishap made D0 unusable on this specific board, so the
strip moved down one pad. Nothing about the XIAO requires this — a fresh
build should still start at D0/GPIO2. Recorded here rather than in the
board file precisely because it's a fact about *this unit*, which is the
board-file/system-file split this directory is built on.

**`config.py` for this unit therefore needs `LED_PIN = 3`.**

### IMU — 4 wires

| XIAO C3 | Physical position (USB-C up) | GPIO | → | AE-LSM6DSV16X |
|---|---|---|---|---|
| 3V3 | right side, 3rd from top | — | → | VCC |
| GND | right side, 2nd from top | — | → | GND |
| D4 | left side, 5th from top | `6` | → | SDA |
| D5 | left side, 6th from top | `7` | → | SCL |

Connector wire order as built, left → right: **SCL, SDA, 3V3, GND**.

**`config.py` values**: `LED_PIN = 2`, `NUM_LEDS = 21`, `IMU_SDA_PIN = 6`,
`IMU_SCL_PIN = 7`, `IMU_I2C_ID = 0`, `HEARTBEAT_PIN = None`.

## ⚠ Power rails: shared GND, separate positives

Same rule `pico2w.md` documents for its own combined build — restated here
because getting it wrong destroys the IMU, not just the run:

| Signal | XIAO pin | Shared? |
|---|---|---|
| GND | GND (right, 2nd) | ✅ **yes** — both devices, one common rail |
| IMU VCC | **3V3** (right, 3rd) | ❌ IMU only — the LSM6DSV16X is **not** 5V-tolerant |
| LED VCC | **5V** (right, 1st) | ❌ LED only — needs real 5V, would over-volt the IMU |

**Do not bridge 3V3 and 5V.** GND is the only rail meant to be common.

### The one-GND-pad splice

The XIAO breaks out exactly **one** GND pad, and this build needs two grounds
on it. Don't make two joints on one small pad — that's how pads lift. Twist
both ground wires into a single lead, solder the twist, heat-shrink, then make
**one** joint to the pad. Technique + wire-gauge notes: `docs/hardware.md`
§ Build technique.

## Strip pigtail pad order — as wired here

Held in the orientation used for this build, the input pigtail reads top →
bottom: **5V, DIN, GND**. Confirmed working (`make led-test` drives all 21).

⚠ **This does not automatically resolve
[v1.4-gift-jar-system.md](v1.4-gift-jar-system.md)'s open ⚠** about its
middle pad. That file records the order "LEDs facing DOWN", a different
reference orientation, and reading a 3-pad pigtail from the opposite face
reverses it. Same strip type, so the answer is probably in here — but confirm
against the physical part in *that* file's stated orientation before flipping
its status, rather than copying this row across. (A five-minute multimeter
check versus a lost bring-up session — the same tradeoff that file already
argues for.)

## Bring-up sequence used

Full walkthrough: [`docs/provisioning-runbook.md`](../docs/provisioning-runbook.md).

```
make flash-esp32-c3     # MicroPython onto a fresh XIAO
make upload             # main.py + config.py + schedule.json (runs make test first)
make led-test           # all 21 LEDs — confirms LED_PIN/NUM_LEDS
make imu-test           # I2C scan + WHO_AM_I — confirms IMU pins/wiring
```

**Bring-up scripts are per-board constants, not config-driven** — by design,
but it means a board swap needs a hand edit in each. Every one of them now
echoes its pins on the first line so a stale value shows up immediately
instead of as a confusing empty scan. `imu_test.py`'s `SDA_PIN`/`SCL_PIN`
were the specific thing that bit during this build (still on Pico 2W's 0/1;
the XIAO doesn't even expose GPIO0/GPIO1).
