# v1.6 — RP2350 production unit (21-LED + IMU + DS3231)

**Status: ⬜ Proposed for the soldered assembly.** Every electrical fact below
is bench-verified on breadboard (2026-08-22 → 08-25): all three peripherals
working together, both I²C devices sharing one bus, firmware reading the
DS3231 and surviving a power cycle. What is *not* yet done is the soldered
build in a vessel. Flip to ✅ once that runs.

> **On the name.** V1.6 was a *firmware* milestone (the single-target module
> split, `docs/v1.6-refactor.md`). This is the *hardware* it was written for,
> and the two landed together — the radio-less RP2350 is the whole reason the
> firmware stopped carrying WiFi. V1.5 is separately reserved for the round
> PCB LED ring, which is unbuilt.

**This file is self-contained on purpose.** Everything needed to wire this
unit is here; the detail it links to is background, not prerequisite.

| | |
|---|---|
| MCU | Seeed XIAO RP2350 — [board file](xiao_rp2350.md) |
| Display | 21× WS2812B strip |
| Motion | AE-LSM6DSV16X IMU breakout (I²C `0x6B`) |
| Clock | Adafruit DS3231 #3013 + CR1220 (I²C `0x68`) |
| Power | USB-C (Qi later — `docs/roadmap.md` v1.1) |

## 2. XIAO RP2350 — every pin, and what this build uses

```
                 ┌─────────────┐
                 │   USB-C     │
                 └──┬───────┬──┘
     D0 / GPIO26 ───┤       ├─── 5V     →  strip 5V          ●USED
     D1 / GPIO27 ───┤       ├─── GND    →  GND rail          ●USED
     D2 / GPIO28 ───┤RP2350 ├─── 3V3    →  3V3 rail          ●USED
     D3 / GPIO5  ───┤       ├─── D10 / GPIO3
     D4 / GPIO6  ───┤       ├─── D9  / GPIO4       ●USED = wired here
       └─ SDA → IMU + RTC          ●USED
     D5 / GPIO7  ───┤       ├─── D8  / GPIO2
       └─ SCL → IMU + RTC          ●USED
     D6 / GPIO0  ───┤       ├─── D7  / GPIO1  →  strip DIN   ●USED
                    └───────┘
```

**Free for expansion:** D0, D1, D2, D3, D6, D8, D9, D10 — eight pins,
including SPI (D8/D9/D10) for the NFC reader in `docs/nfc-provisioning.md`
§8.5.

**Onboard, no wiring needed:** `Pin("NEOPIXEL")` — a full-colour status
indicator, power-gated by `NEOPIXEL_POWER` (active-high). `Pin("LED")` is
active-low. Both confirmed 2026-08-23; see the board file.

## 3. Peripheral pads

**21× WS2812B strip — 3 wires. ✅ Pad order confirmed on the physical part
2026-08-25.**

Orientation matters more than the answer does, so state it exactly: hold the
strip with the **pigtail end UP and the LEDs running downward** — i.e. the LED
side is *below* the pads. Read top → bottom:

```
        ┌───────────┐
        │  ●  5V    │   ← top
        │  ●  DI    │
        │  ●  GND   │
        └─────┬─────┘
              │
        ▓▓▓▓▓▓▓▓▓▓▓▓▓   ← LEDs run downward from here
        21× WS2812B
```

Matches the order recorded on the v1.4 IMU dev unit, so both builds of this
strip type agree. ⚠ This does **not** settle
[v1.4-gift-jar-system.md](v1.4-gift-jar-system.md)'s open ⚠ — that file states
its order against "LEDs facing DOWN", a reference to which *face* is toward
you rather than which *end* is up, and reading a 3-pad pigtail from the
opposite face reverses it. Confirm that one in its own stated orientation.

| Strip pad | → | XIAO |
|---|---|---|
| 5V | → | **5V pin** (not 3V3 — WS2812B wants 5V) |
| DIN | → | **D7 / GPIO1** |
| GND | → | GND rail |

### ⚠ THE TWO I²C BREAKOUTS ARE MIRRORED — in BOTH pairs

Physical pad order, confirmed against each part's official documentation
2026-08-25:

```
   DS3231 RTC                       LSM6DSV16X IMU
   (sensor face up, left → right)   (left → right)

   ┌──────┬──────┬──────┬──────┐    ┌──────┬──────┬──────┬──────┐
   │ 3V3  │ GND  │ SCL  │ SDA  │    │ GND  │ 3V3  │ SDA  │ SCL  │
   └──┬───┴──┬───┴──┬───┴──┬───┘    └──┬───┴──┬───┴──┬───┴──┬───┘
      │      │      │      │           │      │      │      │
     3V3    GND    GP7    GP6         GND    3V3    GP6    GP7
     rail   rail   (D5)   (D4)        rail   rail   (D4)   (D5)

      ▲ power: 3V3 then GND              ▲ power: GND then 3V3   ← SWAPPED
        bus:   SCL then SDA                bus:   SDA then SCL   ← SWAPPED
```

**Both pairs are reversed between the two boards.** The bus swap is harmless
— a silent I²C bus and nothing else. **The power swap is not:** wiring the
second board from muscle memory of the first puts 3V3 into a GND pad, which
can damage a part before anything is ever read. Count the pads on each board
separately; do not pattern-match from the other.

> The v1.4 IMU dev unit records this same connector as *"left → right: SCL,
> SDA, 3V3, GND"* — the exact reverse. Same physical part, opposite reading
> reference. The order above is the one confirmed against official docs; if
> the two ever appear to disagree, the disagreement is about which way you are
> holding it, not about the part.

**AE-LSM6DSV16X IMU — 4 wires.**

| pos | IMU pad | → | XIAO |
|---|---|---|---|
| 1 | GND | → | GND rail |
| 2 | 3V3 (VIN) | → | 3V3 rail — ⚠ **never 5V** |
| 3 | SDA | → | D4 / GPIO6 |
| 4 | SCL | → | D5 / GPIO7 |

**DS3231 #3013 RTC — 4 wires**, same bus as the IMU.

| pos | RTC pad | → | XIAO |
|---|---|---|---|
| 1 | 3V3 (VIN) | → | 3V3 rail — ⚠ **never 5V**, its pull-ups tie to VIN |
| 2 | GND | → | GND rail |
| 3 | SCL | → | D5 / GPIO7 |
| 4 | SDA | → | D4 / GPIO6 |

CR1220 fitted, `+` face up. It is what makes the clock survive unplugging.

> **Which physical end is arm A?** With `ARC_ORIGIN = "far"` arm A occupies
> physical LEDs 0–9 (the DIN/pigtail half) and arm B 11–20; `"near"` swaps
> them. Diagram and the mounting caveat:
> `docs/contracts/approach-contract.md` § Physical orientation. ⚠ The final
> answer is per-unit — it depends on which end you wound from and which way
> the LEDs face, so confirm it on the assembled jar and record it in that
> unit's registry entry (`docs/gift-registry.md`).

## 4. `config.py` — the authoritative set for this unit

```python
LED_PIN        = 1      # D7
NUM_LEDS       = 21
HEARTBEAT_PIN  = None   # the "LED" alias exists but is ACTIVE-LOW → inverted
IMU_I2C_ID     = 1      # ⚠ NOT 0 — see §5
IMU_SDA_PIN    = 6      # D4
IMU_SCL_PIN    = 7      # D5
TIME_SOURCE    = "ds3231"
GESTURE_ENABLED    = True
MARKER_BRIGHTNESS  = 0.25   # ⚠ NOT 0.15 — see §5
```

`RTC_I2C_ID` / `RTC_SDA_PIN` / `RTC_SCL_PIN` default to the IMU's values, so
they need no entry while both share this bus.

## 5. The five traps, all of which have cost a session

1. **`IMU_I2C_ID = 1`, not 0.** On RP2350 each I²C peripheral is fixed in
   silicon per pin: GP6/GP7 is I²C**1**. A wrong ID is rejected at
   *construction* with a bare `ValueError: bad SCL pin`, before any bus
   activity — **no rewiring can fix it.** Four sessions. `make i2c-scan`
   re-derives it.
2. **A wrong `LED_PIN` is a POWER fault, not a display bug.** An unaddressed
   WS2812B strip holds whatever state it powered up in — see §6.
3. **`MARKER_BRIGHTNESS` at or below 0.15 makes markers read RED.**
   80 × 0.15 × 0.15 = raw 1, exactly where WS2812B channels stop matching.
   Measured floor is 3. `docs/insights.md` §12.
4. **A fitted CR1220 HIDES a power fault on the RTC.** The DS3231 disables
   its I²C whenever it runs on VBAT, so a sagging VIN gives a chip that is
   alive, keeping perfect time, and *invisible to a scan*. The diagnostic:
   if pulling the cell makes it appear, VIN is below ~2.6 V.
5. **Firmware older than 2026-04-06 corrupts this board's filesystem.**
   v1.28.0 builds size the filesystem at 3072 KB on a 2 MB part
   ([pico-sdk#2834](https://github.com/raspberrypi/pico-sdk/issues/2834),
   [micropython#18839](https://github.com/micropython/micropython/issues/18839)).
   `make doctor` fails such a board; a correct one reports ~1408 KB.

## 6. Power — 21 LEDs is a different regime from 8

WS2812B draws ~60 mA per LED at full white (20 mA per channel):

| state | current | vs USB-2.0 500 mA |
|---|---|---|
| all 21 full white, raw | **1,260 mA** | **2.5× over — will trip** |
| all 21 white at `BRIGHTNESS = 0.15` | ~190 mA | fine |
| typical display (anchor + 2–6 lit) | ~30–60 mA | fine |
| dark but powered (quiescent) | ~17 mA | fine |

**The hazard is the first row, and it is reached by accident, not by
configuration.** A strip that never receives data holds its power-up state,
and `BRIGHTNESS` cannot govern data you are not sending. On 2026-08-23 that
stalled the board with only *8* LEDs attached; 21 is 2.6× worse.

So: **verify `LED_PIN` before connecting the strip**, and bring a strip up
with `make led-test` (which carries its own `DATA_PIN`, independent of
`config.py`) rather than by running `main.py`.

## 7. Bring-up order

Each step proves one thing and needs the previous to have passed.

```
  1  make doctor                     board healthy, filesystem ~1408 KB
  2  make i2c-scan                   0x68 + 0x6B on I2C1 SDA=6 SCL=7
  3  make imu-test                   WHO_AM_I = 0x70, live accel
  4  make rtc-test                   OSF set + year 2000 on a fresh chip is
                                     EXPECTED — seed it: runbook §5b
                                     (check the HOST clock first; its error
                                      is copied into the unit permanently)
  5  make led-test                   all 21 cycle — ⚠ strip attached only NOW
  6  make low-pwm-test               confirm the floor on THIS strip (21 ≠ 8)
  7  make upload && make screen      Ctrl-D; full loop
```

Full procedure with the reasoning: `docs/provisioning-runbook.md`.
`make dev` runs the firmware from the host with **zero flash writes** — the
right loop for tuning once the wiring is proven.
