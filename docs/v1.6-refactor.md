# V1.6 — single-target firmware for the XIAO RP2350

**Status: planned, not started.** Branch: `feature/v1.6-single-target`.
Proposal and rationale: `dev-status.md` § V1.6. This file is the *how*.

---

## Goal

Split `main.py` (3,127 lines / 154 KB) into modules, then build a thin
production top level on top of them that **contains no radio code at all**.
The existing multi-board firmware survives as a bench reference.

## Non-goals — read these first

- **This is not a rewrite.** The `time → LeaveSignal → DisplayContract →
  LEDs` pipeline is validated and pinned by 260 host tests. It gets *moved*,
  not reimplemented. Any step that changes behaviour has gone wrong.
- **This is not a memory optimisation.** A bare XIAO RP2350 has 492 KB free
  and the whole firmware costs ~55 KB. Memory is not a constraint on this
  board and must not be cited as a reason for anything here.
- **This does not change the display.** No contract, colour, gamma or
  gesture behaviour changes. If the LEDs look different, revert.

## Why it's worth doing

1. **Capability differences don't belong in `config.py`.** `import network`
   at line 17 meant `main.py` could not run *at all* on a radio-less board,
   and `TIME_SOURCE="rtc"` could not save it — the failure lands before
   config is read. A hardware fact became something you must remember to
   declare correctly, every time.
2. **Upload cost.** `main.py` is 154 KB, rewritten in full on every upload,
   and upload duration is a live suspect in the intermittent transfer
   failures (`insights.md` §13). After the split you re-upload only what
   changed — usually a few KB.
3. **The Rust port needs these boundaries anyway.** Module edges here become
   crate and `mod` edges under Embassy. The hard part of that port is
   deciding what the units *are*; settling it in a language you can iterate
   in overnight is far cheaper than discovering it in the borrow checker.

## The one rule that keeps this safe

**`main.py` re-exports everything during the transition.**

```python
from primitives import *   # noqa: F401,F403  — transitional re-export
```

260 tests reach into `main.X`, and `tests/conftest.py`'s `load_main` fixture
imports `main` specifically. Re-exporting means **the test suite never has
to change while the code moves**, so a green suite genuinely proves nothing
broke. Tighten the imports (and update tests) only once every module has
landed — as a separate, final commit.

Do not skip this. Moving code *and* rewriting tests in the same step
destroys the only evidence that the move was faithful.

**`import *` does not export underscore-prefixed names.** This has bitten
every extraction so far — `settings` needed `_UTC_OFFSET_APPLIED`,
`primitives` needed `_rgb_to_hsv`/`_hsv_to_rgb`, `diag` needed all three of
its privates. The tests reach into `main._something` and fail with a bare
`AttributeError: module 'main' has no attribute …`, which reads like a
botched extraction when it's only a visibility rule. List them before you
cut:

```bash
grep -nE '^(_[A-Za-z0-9_]+ *=|def _[A-Za-z0-9_]+)' micropython/<module>.py
```

then add one explicit `from <module> import _a, _b` line alongside the star
import.

## Runbook

Work one module per commit. **`make test` must be green before every
commit** — if it isn't, the extraction was not faithful.

### Before you start

```bash
git checkout feature/v1.6-single-target
make test            # baseline: 265 passing
cp micropython/main.py /tmp/main-v15-reference.py   # for diffing later
```

### ⚠ `global X` does NOT move with the function that declares it

`_get_imu()` is a lazy singleton: it declares `global _imu_i2c` and READS it
before ever assigning. The initialisers `_imu_i2c = None` sat above the
banner comment and stayed in main.py, so the extracted function referred to
a module global that did not exist — `NameError` on hardware, from a green
suite.

Nothing could catch it. A `global X` declaration makes X look defined to
ruff's F821 *and* to the private-name check, and in general that is correct
— a global can be created by first assignment inside a function. It is only
a bug when the function reads before writing, which is exactly the pattern
this firmware uses for every piece of hardware (`_imu_i2c`, `_rtc_i2c`,
`_rtc_cache`). And `_get_imu()` is I/O, so no host test reaches it.

`tests/test_module_wiring.py::test_declared_globals_exist_at_module_level`
now flags any `global` with no module-level assignment. When you extract a
function, take its initialisers with it:

```bash
grep -nE '^\s*global ' micropython/main.py   # before cutting
```

### ⚠ A star-import COPIES values — mutable globals break silently

`BRIGHTNESS` is mutated at runtime by `_cycle_brightness()`. After the split
`gestures.py` rebound *its own* copy while `leds._write_frame` kept reading
another — so brightness cycling would have silently stopped working on
hardware **with every test passing**, because the test asserted on
`main.BRIGHTNESS`, a third stale copy.

Any value that changes at runtime needs **one home, read by attribute**:

```python
import settings          # NOT `from settings import *`
... settings.BRIGHTNESS  # reads the live value every time
```

Before extracting a module, list what it mutates — `grep -n '^\s*global '`.
Module-private globals (`_rtc_cache`, `_imu_i2c`) are fine; anything another
module reads is not.

### ⚠ A green suite is NOT proof the wiring is right

`tests/test_module_wiring.py` exists because the ordinary suite structurally
cannot check this. It only covers paths it exercises, and boot-time hardware
paths are exactly the ones it can't reach. Two real bugs got that far:

- `run_startup_sequence()` called `clock._check_ds3231_at_boot()` with no
  import — a `NameError` at boot, on the DS3231 path, with 265 tests green.
- `clock.py` used `settings._UTC_OFFSET_APPLIED` through a star-import that
  skips it — inside `_ds3231_local_time()`, the live runtime path.

The wiring test is static (AST over each module), so it needs no coverage at
all. Run it after every extraction; it found the second bug the moment it
was written.

### ⚠ The map is a sketch — re-derive dependencies before each cut

The table above was written from banner comments and is **wrong in places**.
Two corrections found by doing it:

- `_physical()` reads like contract geometry but is used only by
  `_write_frame`/`_paint_layers`, so it belongs in **leds.py**. Putting it
  with the contracts would have made leds depend on contracts and inverted
  the whole layering.
- `next_departures()` sat in the "Schedule logic" section but is called by
  `leave_signal()`, so **signals.py** would have depended on a module
  extracted five steps later. It moved to signals.py, where it is anyway the
  first half of stage 1: timetable → minutes-until → `LeaveSignal`.

Before cutting, list where each name is actually used:

```bash
for n in <names>; do printf "%-18s " "$n"; \
  grep -n "\b$n\b" micropython/main.py | awk -F: '{printf "%s ", $1}'; echo; done
```

A dependency pointing *backwards* means the map is wrong, not the code.

### ⚠ Every new module must be added to `scripts/upload.sh`

`main.py` imports them, so a module missing from the board is an
`ImportError` at boot. **The host tests cannot catch this** — they import
from the source tree, where the file obviously exists. Add the module to
`FIRMWARE_MODULES` in `scripts/upload.sh` in the *same commit* that creates
it, or the first person to `make upload` gets a dead unit and a green suite.

### Per-module loop

For each module in the order below:

1. Create `micropython/<module>.py` with the project's header-comment style
   (what it is, why it exists, what depends on it).
2. **Cut** the lines from `main.py` and **paste** them in. Do not retype and
   do not "tidy while you're there" — a faithful move is the entire point.
3. Add the module's own imports at its top.
4. In `main.py`, add `from <module> import *` where the code used to be.
5. Add it to `FIRMWARE_MODULES` in `scripts/upload.sh`.
6. `make test` — must still be 265 passing.
7. Commit: `refactor: extract <module> from main.py (no behaviour change)`.

### Order — leaves first, so nothing you extract depends on something still moving

```
1. settings.py      ← DONE (b/o this branch)
2. diag.py          ← DONE
3. primitives.py    ← DONE
4. signals.py       ← DONE
5. leds.py          ← DONE
6. contracts.py     ← DONE (the big one: 431 lines)
7. schedule.py      ← DONE
8. clock.py         ← DONE
9. gestures.py      ← DONE
10. status.py       ← DONE (display only; see below)
11. net.py          ← extract LAST, so the deletion below is a clean removal
```

### Then the actual feature

12. **`main_bench.py`** — copy `main.py`, keep its `net` import, keep
    `TIME_SOURCE="wifi"` support. This is the multi-board bench reference.
13. **Strip `main.py`**: delete the `net` import, the `connect_wifi` /
    `sync_ntp` call sites, and the `"wifi"` branch of `run_startup_sequence`.
    `TIME_SOURCE` becomes `"ds3231" | "rtc"`. The guarded
    `try: import network` goes away entirely — there is nothing to guard.
14. **Update `make upload`** to skip `net.py` for XIAO targets.
15. **Tighten imports** — DONE. Zero star-imports remain. Notes below.

### Verification at the end

```bash
make test                                   # still 260 (or more)
make upload && make screen                  # Ctrl-D, watch the boot
```

The boot output must be **byte-identical** to v1.5's apart from the absent
WiFi lines. Diff it against a capture from before you started. Then power-
cycle and confirm the DS3231 path still comes up — that is the regression
that would matter most.

## What the tightening step actually involved

Worth reading before doing this on another codebase — it was the step with
the most surprises.

**A facade in `conftest`, not 636 test edits.** The tests reach through the
module object for 99 names, 97 of which no longer live in `main.py`.
`load_main()` now returns a facade resolving across every firmware module —
so the suite still verified the refactor without being rewritten by it.
Crucially the facade resolves to the module that **defines** a name, not one
that imported it, because an imported name is a copy.

**Bring-up scripts broke, and the tests could not see it.**
`gesture_sandbox.py` and `led_sandbox.py` do `import main` and reach into it
for 40+ names. Their call sites were rewritten to the owning modules.
`gesture_sandbox.py` also did `setattr(main, name, value)` to override
thresholds for a session — that now targets `gestures`, the module that
READS them, not `settings`, which merely defines them. Setting them on
`settings` would have changed a value nothing reads. Same trap as BRIGHTNESS.

**Two failed attempts at the automated rewrite**, both worth naming:
1. Line-based editing mangled multi-line `from x import (...)` blocks. Use
   `ast` node `lineno`/`end_lineno` spans instead.
2. Names already present in an explicit import counted as "already bound",
   so they were left out of the regenerated list — and then their import
   line was deleted. Exclude the imports you are regenerating from the
   bound-name set.

Both were caught by the suite immediately. `git checkout -- micropython/`
and retry is cheap; keep the extraction and the tightening in separate
commits so this stays true.

**The payoff is `ruff`.** `F821` (undefined name) is exactly the check that
star-imports disable — which is why two NameErrors on the DS3231 boot path
survived a green 278-test suite. `make test` now runs `make lint` first.
`tests/test_module_wiring.py` stays as a backstop: it needs no dependency
and no path coverage.

## Open design question: a status channel

The XIAO RP2350 has an **onboard NeoPixel** on a board-defined alias
(`Pin("NEOPIXEL")`, power-gated by `NEOPIXEL_POWER`) — confirmed working,
`pinouts/xiao_rp2350.md`.

Its value is specifically diagnostic, and today made the case: when
`LED_PIN` was wrong, there was **no feedback at all**, because the only
output device was the one being misconfigured. The onboard NeoPixel cannot
be misconfigured — its pin comes from the board definition, not `config.py`.
It is the one indicator that still works when config is wrong.

If it happens, it belongs in `status.py` as a second output behind the same
`led-status-messages.md` vocabulary — **not** a `DisplayContract`. It shows
device state, not departures, and giving it a contract would confuse two
different things.

Scope it honestly: this is a **bring-up and development** aid. Inside a
frosted jar the onboard LED is either invisible or a distraction, and
`NEOPIXEL_POWER` exists to switch it off in production. Worth doing because
it makes the *next* misconfiguration cheap to diagnose — not because the
finished product needs it.
